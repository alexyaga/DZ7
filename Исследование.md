# AI Meeting Analyzer — исследование перед этапом 1

## Компоненты для переиспользования

- Каркас интерфейса — [официальный шаблон React для Vite](https://github.com/vitejs/vite/tree/main/packages/create-vite/template-react). Backend — Express.
- Загрузка — [Multer](https://github.com/expressjs/multer) с записью на диск, ограничением размера и одним файлом на запрос. Фактический контейнер, длительность и аудиопоток проверяет ffprobe.
- Медиа — отдельные Windows-бинарники [FFmpeg и ffprobe](https://ffmpeg.org/download.html), вызов из Node.js через spawn с массивом аргументов. Это переносит проверенный в «Конспектах лекций» подход к путям с пробелами и кириллицей. fluent-ffmpeg архивирован.
- Облако — [официальный SDK OpenAI для Node.js](https://github.com/openai/openai-node), явный таймаут и maxRetries: 0. Для конспекта — [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) и проверка схемы на сервере.
- JSON — [write-file-atomic](https://github.com/npm/write-file-atomic) для записи снимка. Сериализовать всю операцию чтения, изменения и записи в репозитории, чтобы параллельные обновления не затёрли друг друга.
- [Meetily](https://github.com/Zackriya-Solutions/meetily) — пример интерфейса просмотра транскрипции и итогов. Его архитектура с настольным приложением и локальным распознаванием отличается от стека Light.

## Предлагаемая архитектура

`frontend/` — React, запросы к API и отображение статуса. `backend/` — Express, маршруты, независимые модули обработки медиа, транскрибации, конспекта и репозитория. `data/meetings.json` — локальная история, `data/tmp/<id>/` — рабочие файлы. API и интерфейс Light слушают loopback.

POST /api/meetings/upload принимает один MP4/WebM, валидирует файл, создаёт запись и возвращает 202 с ID. Независимый обработчик processMeeting(meetingId, videoPath) извлекает MP3, получает и сохраняет транскрипцию, затем сохраняет конспект. GET /api/meetings возвращает историю, GET /api/meetings/:id — подробности, GET /api/health — доступность сервера.

Запись хранит UUID, имя файла, дату в UTC, источник manual, статус processing/completed/error, transcript, summary и error. На старте прерванное задание переводится в ошибку с сохранением уже записанной расшифровки. Неопределённые облачные запросы автоматически не повторяются.

## Этапы и проверки

1. React/Vite, Express и health-маршрут. Проверить запуск и соединение из браузера.
2. Загрузка. Проверить MP4, WebM, неверный контейнер, отсутствие аудиопотока и лимиты.
3. Извлечение аудио. Проверить MP3, пути Windows, таймаут и очистку временных файлов.
4. Транскрибация. Проверить ошибки на имитациях API. Реальную пробу провести с разрешением на конкретный файл и расходы.
5. Конспект. Проверить схему, пустые поля, отсутствие выдуманных сроков и сохранение транскрипции при ошибке.
6. История. Проверить атомарную запись, восстановление после перезапуска и ограничение одной активной задачей.
7. Приёмка Light на Windows 10 и документация. Каждый следующий этап запускается отдельной командой пользователя.

## Риски и решения для следующих этапов

- OpenAI [назначила отключение gpt-4o-mini-transcribe на 26 февраля 2027 года](https://developers.openai.com/api/docs/deprecations). До этапа 4 согласовать переход на gpt-transcribe. Ограничение аудиозагрузки — [25 МБ](https://developers.openai.com/api/docs/guides/speech-to-text).
- До платной обработки согласовать, как автоматически запускать её после загрузки при подтверждённой оценке и лимите расходов.
- Записи 2–5 минут — целевой сценарий. Верхние границы длительности и размера следует закрепить до этапа загрузки.
- Для проверки качества нужны реальные русскоязычные MP4 и WebM, в том числе тишина и обсуждение, в котором предложения не стали решениями.

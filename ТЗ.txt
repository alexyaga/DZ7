# Техническое задание: AI Meeting Analyzer — Light → Pro

## 1. Назначение проекта

Разработать учебное веб-приложение **AI Meeting Analyzer** для автоматического анализа видеозаписей встреч из Zoom и Яндекс Телемоста.

Приложение должно принимать реальные видеозаписи, извлекать из них аудио, распознавать речь с помощью OpenAI API и формировать структурированный AI-конспект встречи.

Проект разрабатывается последовательно в двух версиях:

**Light — локальное приложение:**
- Frontend и backend работают на компьютере под Windows 10.
- Пользователь загружает видеозапись с компьютера.
- Обработка начинается автоматически.
- Расшифровка и конспект сохраняются локально.

**Pro — гибридная архитектура:**
- Frontend размещается на Vercel.
- Backend продолжает работать на локальном компьютере.
- Связь осуществляется через Cloudflare Tunnel.
- Добавляется импорт видеозаписей из Яндекс Диска по ссылке.
- Используются те же модули транскрибации и AI-анализа, что и в Light.

**Важно:** сначала необходимо полностью реализовать и протестировать Light. Не приступать к функциям Pro до завершения Light.

## 2. Технологический стек

Использовать следующие технологии:

| Компонент | Технология |
|---|---|
| Язык программирования | JavaScript |
| Frontend | React + Vite |
| Backend | Node.js + Express |
| Извлечение аудио | FFmpeg и ffprobe |
| Распознавание речи | OpenAI `gpt-4o-mini-transcribe` |
| Создание AI-конспекта | OpenAI API, отдельная текстовая модель |
| Хранение результатов | Локальный JSON-файл |
| Взаимодействие frontend/backend | REST API |
| Контроль версий | Git |
| Публикация Pro | Vercel |
| Доступ к локальному backend в Pro | Cloudflare Tunnel |

Не использовать Groq API.

Для транскрибации и создания конспекта использовать один OpenAI API-ключ, но отдельные модели и программные сервисы.

## 3. Общая архитектура

Разделить приложение на независимые компоненты:

1. Frontend — пользовательский интерфейс.
2. Backend — REST API и управление задачами.
3. Video Processor — обработка видеозаписей.
4. Audio Extractor — извлечение аудио.
5. Transcription Service — транскрибация через OpenAI.
6. Summary Service — создание AI-конспекта.
7. Meeting Repository — сохранение истории и результатов.

Все вызовы OpenAI API выполнять исключительно на backend.

Frontend не должен иметь доступа к секретному API-ключу.

### Ключевое архитектурное требование

Разработать единую функцию обработки встречи:

`processMeeting(meetingId, videoPath)`

Она должна:

1. Проверить доступность видео.
2. Извлечь аудиодорожку.
3. Выполнить транскрибацию.
4. Сохранить расшифровку.
5. Создать AI-конспект.
6. Сохранить конспект.
7. Обновить статус встречи.
8. Удалить ненужные временные файлы.

Функция не должна зависеть от происхождения видеофайла.

В Light она вызывается после ручной загрузки, в Pro — также после скачивания видео из Яндекс Диска.

## 4. Функциональность Light

### 4.1. Загрузка видео

Реализовать загрузку файлов MP4 и WebM.

Требования:
- Основная продолжительность записей — 2–5 минут.
- Обрабатывать одну запись одновременно.
- Проверять расширение и фактический тип файла.
- Проверять размер и длительность.
- Проверять наличие аудиодорожки.
- Автоматически начинать обработку после загрузки.
- Не требовать подключения аккаунтов Zoom или Яндекс Телемоста.

При некорректном файле показывать понятное сообщение об ошибке.

### 4.2. Извлечение аудио

Для извлечения звуковой дорожки использовать FFmpeg.

Требования:
- Поддерживать MP4 и WebM.
- Преобразовывать аудио в формат, поддерживаемый OpenAI Audio Transcriptions API.
- Рекомендуемый выходной формат — MP3.
- Использовать монофоническое аудио с подходящими параметрами качества.
- Сохранять разборчивость речи.
- Контролировать размер аудиофайла перед отправкой.
- Не отправлять в OpenAI исходное видео, если достаточно извлечённого аудио.

Предусмотреть обработку ошибок FFmpeg и отсутствие аудиодорожки.

Временный аудиофайл можно удалять после успешной транскрибации.

### 4.3. Транскрибация через OpenAI

Использовать официальный OpenAI Audio Transcriptions API.

Модель:

`gpt-4o-mini-transcribe`

Требования:
- Основной язык аудио — русский.
- Отправлять реальное аудио, извлечённое из видеозаписи.
- Получать текст распознанной речи.
- Сохранять полную расшифровку.
- Не создавать фиктивные транскрипции.
- Не придумывать слова при отсутствии речи.
- Обрабатывать ошибки сети, API и превышения лимитов.
- Не повторять платный запрос бесконтрольно.

Реализовать отдельный модуль:

`transcriptionService.js`

Основная функция:

`transcribeAudio(audioPath)`

Функция должна возвращать распознанный текст.

Не связывать её напрямую с интерфейсом или файловым хранилищем.

В будущем должна существовать возможность заменить модель транскрибации через конфигурацию без переработки остального приложения.

### 4.4. Создание AI-конспекта

После получения транскрипции отправлять её в отдельную текстовую модель OpenAI.

Создавать четыре раздела:

1. Краткое содержание встречи.
2. Принятые решения.
3. Задачи после встречи.
4. Открытые вопросы.

Использовать структурированный JSON-ответ следующего вида:

```json
{
  "summary": "Краткое содержание встречи",
  "decisions": [
    "Принятое решение"
  ],
  "tasks": [
    {
      "description": "Описание задачи",
      "assignee": null,
      "deadline": null
    }
  ],
  "open_questions": [
    "Нерешённый вопрос"
  ]
}
```

Требования:
- Анализировать только содержание реальной расшифровки.
- Не выдумывать решения и факты.
- Не придумывать участников и исполнителей.
- Не придумывать сроки.
- Отличать обсуждаемые предложения от принятых решений.
- Если информация отсутствует, возвращать пустые массивы или `null`.
- Проверять JSON-ответ на backend.

Модель для конспекта должна задаваться отдельной переменной окружения.

Реализовать модуль:

`summaryService.js`

Функция:

`generateMeetingSummary(transcript)`

### 4.5. Интерфейс пользователя

Создать простое одностраничное приложение.

Обязательные элементы:
- Заголовок «AI Meeting Analyzer».
- Область выбора и загрузки видеозаписи.
- Список встреч.
- Название файла.
- Дата добавления.
- Текущий статус.
- Возможность выбрать встречу.
- Полная расшифровка выбранной встречи.
- Краткое содержание.
- Решения.
- Задачи.
- Открытые вопросы.

Для Light использовать статусы:
- «Обрабатывается».
- «Готово».
- «Ошибка».

Не добавлять аналитическую панель, графики, авторизацию, дополнительные страницы и ненужные функции.

Не отображать фиктивные проценты обработки.

### 4.6. Сохранение истории

Сохранять на локальном диске:
- ID встречи.
- Имя исходного файла.
- Дату добавления.
- Источник `manual`.
- Статус.
- Расшифровку.
- AI-конспект.
- Ошибку, если она возникла.

Использовать JSON-файл.

После обновления страницы и перезапуска приложения история встреч должна сохраняться.

Для защиты от повреждения хранилища предусмотреть последовательную и атомарную запись данных.

Не требуется сохранять исходные видео после завершения анализа.

### 4.7. Фоновая обработка

После загрузки видео backend должен создать запись встречи и вернуть её ID.

Анализ выполняется независимо от исходного HTTP-запроса.

Frontend периодически запрашивает состояние задачи.

Для Light достаточно одной одновременно выполняемой задачи. Сложная система очередей не требуется.

После перезапуска сервера незавершённые задания не должны бесконечно оставаться в статусе «Обрабатывается».

При ошибке AI-конспекта уже полученную транскрипцию необходимо сохранять, чтобы не повторять распознавание без необходимости.

## 5. REST API

Предусмотреть следующие маршруты:

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/health` | Проверка доступности backend |
| POST | `/api/meetings/upload` | Загрузка видео и запуск анализа |
| GET | `/api/meetings` | Получение истории встреч |
| GET | `/api/meetings/:id` | Получение отдельной встречи и результата |

В дальнейшем Pro расширит этот API методом импорта по облачной ссылке.

## 6. Конфигурация

Создать файл `.env.example`:

```env
OPENAI_API_KEY=
OPENAI_TRANSCRIPTION_MODEL=gpt-4o-mini-transcribe
OPENAI_SUMMARY_MODEL=
PORT=3001
DATA_DIR=./data
CLIENT_ORIGIN=http://localhost:5173
VITE_API_BASE_URL=http://localhost:3001
```

Учесть, что переменные `VITE_` предназначены для сборки frontend. Клиентские настройки должны находиться в конфигурации Vite, а секретный ключ — только в конфигурации backend.

Создать `.gitignore`, исключающий:
- `.env`
- `node_modules`
- временные файлы видео и аудио;
- локальную историю встреч с личными данными;
- другие секретные и генерируемые файлы.

## 8. Требования к качеству

Приложение должно:
- Использовать реальные AI API.
- Корректно обрабатывать ошибки.
- Не показывать вымышленные результаты.
- Сохранять данные между запусками.
- Не допускать утечки API-ключа.
- Работать на Windows 10.
- Иметь понятную инструкцию установки и запуска.
- Иметь независимые модули транскрибации и создания конспекта.

## 9. Этапы реализации

Разрабатывать последовательно:

**Этап 1.** Каркас проекта: React, Express, структура каталогов, конфигурация, тестовый API.

**Этап 2.** Загрузка и проверка видео WebM/MP4.

**Этап 3.** FFmpeg и извлечение аудио.

**Этап 4.** Реальная транскрибация через OpenAI `gpt-4o-mini-transcribe`.

**Этап 5.** Создание структурированного AI-конспекта с помощью отдельной модели OpenAI.

**Этап 6.** История встреч, сохранение результатов и обработка ошибок.

**Этап 7.** Полное тестирование Light и подготовка README.

После каждого этапа:
1. Провести проверку.
2. Сообщить, какие файлы изменены.
3. Указать команды запуска.
4. Исправить ошибки.
5. Не переходить к следующему этапу без отдельной команды.
